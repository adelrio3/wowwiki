# 02. Data Model

## Layers

Data moves through five layers. Lower layers are never edited; higher layers are
always rebuildable from lower ones.

| Layer | Name | Mutability | Contents |
|-------|------|------------|----------|
| L0 | Uploads | Immutable while retained | Raw SavedVariables files in Storage, plus a row per upload. Retained 90 days; first 3 per (flavor, build) kept as fixtures (D-0023). |
| L1 | Observations | Immutable, append-only, compacted | Normalized records extracted from uploads. One row per (contributor, session, entity, field, value). Compacted per (fact, patch) after 50 distinct contributors (D-0023). |
| L2 | Facts | Rebuildable | Aggregated per (flavor, entity, field): value intervals by build, contributor counts, status. |
| L3 | Overrides | Mutable, audited | Admin corrections and hides, each with reason and author. |
| L4 | Views | Derived | What pages render: facts merged with overrides, collapsed to expansion. Materialized where needed. |

The Journal is a parallel set of per-account tables derived from L1 (experiential
observations) plus the achievement engine's output. Journal data is never compacted;
it is the user's own record.

## Retention (D-0023)

| Data | Rule |
|------|------|
| Raw uploads | Deleted 90 days after ingest. The first 3 uploads per (flavor, build) are kept indefinitely as scrubbed fixtures. |
| Observations | Once a (fact, patch) has rows from 50 distinct contributors, new reports increment `facts.contributor_count` and `observation_count` and update the build/time intervals, but no row is written. Existing rows are never deleted except by account deletion. |
| Facts, relations, positions | Rebuildable from retained observations plus the counters; never pruned. |
| Journal | Kept until the user deletes it. |
| Audit log | Kept indefinitely. |

Both numbers are configuration values and may change by decision.

## Cross-check with Blizzard's API (D-0024)

An aggregate-stage job compares confirmed facts with the corresponding Blizzard Game
Data API record where one exists (items and creatures for Era; more for Retail).
Agreement adds a `api_agrees = true` flag on the fact and a small positive trust
adjustment to its contributors. Disagreement writes a row to `api_disagreements`
(fact, api value, observed value, at) for admins and changes nothing else. API values
are not stored as facts and are never rendered.

## Identity

### Contributors and accounts

- `account`: one Compendium account (Supabase Auth user). One per person.
- `addon_identity`: a random UUID generated by the add-on the first time it runs on a
  WoW license, stored account-wide in SavedVariables. The link file (see `04`) binds it
  to an `account`. One account can have several addon identities (multiple WoW
  licenses, multiple flavors share the identity only if their SavedVariables are
  separate; they are, so each flavor folder gets its own).
- We never store the WoW account name from the folder path, and never the BattleTag
  unless the user opts in to display it (see `07`).

### Characters

Key: `(flavor, region, realm_slug, player_guid)`. The player GUID (`Player-<server>-<id>`)
is stable across renames. Name and realm are attributes with history (renames, transfers
produce a new GUID in some cases; we treat that as a new character and offer a manual
merge in the Journal later).

### World entities

Blizzard's numeric IDs are the natural keys and are consistent within a flavor. The same
ID across flavors may describe different things, so every entity key is `(flavor, id)`.

| Entity | ID source | Notes |
|--------|-----------|-------|
| creature | npcID from GUID `Creature-0-...-<npcID>-...` | Also `Vehicle`, `Pet` GUID types recorded with their kind. |
| gameobject | objectID from GUID `GameObject-0-...-<objectID>-...` | Seen via loot source and some interactions only. |
| item | itemID from item link | Variants (suffix, bonus IDs, enchants) stored as attributes of an observed item instance. |
| quest | questID | |
| spell | spellID | |
| map | uiMapID (`C_Map`) | Zones, subzones, continents, instance maps. |
| area | areaID | Subzone names, discovered via `C_Map.GetAreaInfo` / zone text. |
| faction | factionID | Reputations. |
| instance | instanceID from `GetInstanceInfo` | Dungeons, raids, battlegrounds. |
| encounter | encounterID from `ENCOUNTER_START` | Bosses. Falls back to final-boss npcID where encounter IDs are absent. |
| taxi_node | taxi node ID | Flight masters and routes. |
| skill_line | skillLineID | Professions and secondary skills. |
| recipe | spellID of the craft | Links reagents (items) to product (item). |
| achievement | achievementID | Only where the flavor has in-game achievements. |
| currency | currencyID | |
| title | titleID | |
| class/race/spec | Blizzard IDs | Small reference sets, still captured. |
| gossip | hash of (npcID, text) | Gossip text and options. |
| lore_text | hash of (source entity, page index, text) | Books, signs, letters. |
| speech_line | hash of (npcID, kind, text) | NPC say/yell/emote/whisper lines. |
| scene | server-assigned | Sequence of speech lines in one place and window. |

### Fields

Each entity type has a fixed set of fields defined in `packages/schema`. A field is
either:

- **scalar** (level, quality, sell price), aggregated by value with intervals;
- **text** (name, description), aggregated per locale with intervals;
- **relation** (creature → drops item, quest → rewards item), aggregated as edges with
  counts (for drop rates, the counts are "times loot window seen" and "times item
  present").
- **position** (creature seen at map X,Y), aggregated into clustered spawn points.
  Positions carry both the map-relative pair (`map_id`, `pos_x`, `pos_y` from
  `C_Map.GetPlayerMapPosition`) and world coordinates (`instance_id`, `world_x`,
  `world_y` from `UnitPosition`), so clustering can be done in world space and
  rendered on any map.

## Versioning

Every observation carries `flavor`, `build`, `server_time`, `realm`. Facts store, per
field value, the interval `[first_build, last_build]` and `[first_seen_at, last_seen_at]`
in which that value was observed.

- `game-meta` maps `(flavor, build) → patch → expansion`. We maintain this table by
  hand as builds appear; the ingest function flags unknown builds for an admin to
  classify. First known row: `(era, 70003) → 1.15.9 → Classic`.
- **Phases** (progression and Anniversary realms) are realm timelines maintained in
  `game-meta`: `(flavor, realm) → [(phase, start_at)]`. Observations get a phase by
  looking up realm and server time. Phase matters for what exists, not for what a thing
  is, so it is attached to presence facts (first/last seen) rather than attribute facts.
- Readers see one page per `(flavor-group, entity)` with an expansion selector and
  nothing finer (D-0020). Within an expansion, if a field changed across patches, the
  page shows the latest confirmed value for that expansion. Build and patch detail is
  visible only in admin tools.

## Localization

Text fields are stored per locale: `(flavor, entity, field, locale) → value intervals`.
The client locale comes from `GetLocale()`. Pages render in the reader's chosen
locale with fallback to `enUS`, then to any locale available. Entity search indexes all
locales.

## Status rules

Applied per fact (per field value, per locale for text):

| Status | Rule |
|--------|------|
| `unconfirmed` | Observed by exactly one contributor. |
| `confirmed` | Observed by two or more distinct contributors with no conflicting value in the same build range. The threshold is a configuration value; initial value 2. |
| `disputed` | Two or more values for the same scalar field in the same build range, none holding a configured supermajority. |
| `retired` | Entity or value not observed for N builds after being observed, where later builds of the same flavor have observations from other entities in the same zone/instance. Soft signal, not deletion. |
| `overridden` | An override exists for this fact. The override's value is displayed; the original stays in history. |

Trusted contributors (see `05`) count as two contributors for status purposes. This is
how a single tester can see confirmed data during bootstrap without weakening the rule
for the public.

## Schema sketch

Not final DDL. Names are binding; types and indexes are decided in migrations.

```sql
-- L0
uploads(id, account_id, addon_identity, flavor, build, locale, region,
        storage_path, sha256, byte_size, received_at, ingested_at,
        ingest_status, ingest_error, schema_version)

-- L1 (partitioned by flavor; append-only)
observations(id, upload_id, account_id, character_id, session_id,
             flavor, build, locale, region, realm_id, server_time,
             entity_type, entity_id, field, value_kind, value_num,
             value_text, value_json, map_id, pos_x, pos_y,
             instance_id, world_x, world_y)

sessions(id, character_id, upload_id, seq, started_at, ended_at,
         flavor, build, phase)

-- L2 (rebuildable)
facts(flavor, entity_type, entity_id, field, locale, value_hash,
      value_num, value_text, value_json,
      first_build, last_build, first_seen_at, last_seen_at,
      contributor_count, observation_count, status)

relations(flavor, from_type, from_id, rel, to_type, to_id,
          first_build, last_build, numerator, denominator,
          contributor_count, status)      -- drop rates use numerator/denominator

positions(flavor, entity_type, entity_id, map_id, cluster_x, cluster_y,
          instance_id, world_x, world_y, radius, observation_count,
          first_build, last_build)

-- L3
overrides(id, flavor, entity_type, entity_id, field, locale,
          action, value_json, reason, created_by, created_at,
          superseded_by)
audit_log(id, actor_id, action, target, before_json, after_json, at)
api_disagreements(id, flavor, entity_type, entity_id, field, api_json,
                  observed_json, checked_at, resolved_by)

-- Reference (hand-maintained)
builds(flavor, build, patch, expansion, released_at)
realms(id, flavor, region, slug, name, connected_group, first_seen_at,
       trust_level)
realm_phases(realm_id, phase, started_at)

-- Accounts and Journal
accounts(id, created_at, display_name, visibility_json, trust_score,
         role)
addon_identities(id, account_id, flavor, first_seen_at)
characters(id, account_id, flavor, region, realm_id, player_guid, name,
           class_id, race_id, faction, created_at, last_seen_at, ...)
journal_events(id, character_id, session_id, kind, at, map_id, pos_x,
               pos_y, payload_json)
character_stats(character_id, stat_key, value_num, updated_at)
character_state(character_id, kind, key, value_json, as_of)
   -- completed quests, explored areas, reputations, skills, known spells
achievement_progress(character_id, achievement_key, criteria_json,
                     earned_at, points)
account_achievements(account_id, achievement_key, earned_at)
leaderboard_entries(board_key, scope, character_id, value, rank, at)
```

## Size estimates

An active session produces on the order of a few thousand observations. A heavy user
over a year is low millions of observation rows. Postgres handles this comfortably with
partitioning by flavor and indexing on `(entity_type, entity_id)`. Raw uploads are
compressed text in Storage. Data size is not a constraint for the foreseeable future.
